#### 1. **Security Headers Scanning**
- **File:** `dash_penetration/scanner/headers.py`
- **Detects:**
  - Missing Content-Security-Policy (HIGH)
  - Missing X-Frame-Options (MEDIUM)
  - Missing X-Content-Type-Options (LOW)
  - Missing X-XSS-Protection (LOW)
  - Missing Referrer-Policy (LOW)
  - Missing Permissions-Policy (INFO)
  - Missing Strict-Transport-Security (MEDIUM)
  - Missing X-Permitted-Cross-Domain-Policies (LOW)
- **Test Cases:** Comprehensive header validation
- **CWE:** CWE-693



A security header is an HTTP response header that tells a web browser how it should handle content and interact with a web application from a security perspective. When a browser requests a web page, the web server or application sends back an HTTP response. In addition to the actual page content, the response contains HTTP headers that provide metadata and instructions to the browser.

For example:

```
HTTP/1.1 200 OK
Content-Type: text/html
Content-Security-Policy: default-src 'self'
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
```

The security headers are therefore coming from the HTTP response generated by the target application or its infrastructure. They may be added by:
The web application itself
  - A web server such as Nginx or Apache
  - A reverse proxy or load balancer
  - A CDN or web application firewall
  - Other middleware in front of the application

The browser reads these headers and applies the corresponding security rules.

Purpose
Security headers provide browser-enforced security controls that can reduce the impact of common web attacks and improve the application's security posture. They are generally a form of defense in depth: a missing header does not necessarily mean that an application is directly exploitable, but it can mean that an additional security mechanism is not being used.

The dash-penetration header scanner checks the HTTP response for a defined set of security headers and reports headers that are missing.

2. Individual Security Header Checks

Content-Security-Policy (CSP) — HIGH
Content-Security-Policy controls which scripts, styles, images, frames, and other resources a browser is allowed to load or execute, helping reduce the impact of attacks such as cross-site scripting (XSS).


X-Frame-Options — MEDIUM
X-Frame-Options controls whether the application can be embedded in a frame, helping protect against clickjacking attacks.


X-Content-Type-Options — LOW
X-Content-Type-Options tells the browser not to MIME-sniff certain responses, reducing the risk that content is interpreted as a different type than the server intended.



X-XSS-Protection — LOW
X-XSS-Protection was a legacy mechanism for enabling browser-based XSS filtering, but it is obsolete in modern browsers and should not be considered a primary XSS defense.


Referrer-Policy — LOW
Referrer-Policy controls how much information about the originating URL is included in the Referer header when the browser makes a request to another resource.


Permissions-Policy — INFO
Permissions-Policy allows an application to control which browser features, such as camera, microphone, or geolocation, can be used by the page or embedded content.


Strict-Transport-Security (HSTS) — MEDIUM
Strict-Transport-Security tells browsers to use HTTPS when communicating with the application, helping prevent certain downgrade and insecure-connection attacks.


X-Permitted-Cross-Domain-Policies — LOW
X-Permitted-Cross-Domain-Policies controls how certain Adobe-related client applications can access resources across domains and is primarily a legacy security-hardening mechanism.


3. CWE-693 — Protection Mechanism Failure

CWE-693 (Protection Mechanism Failure) describes situations where an expected security protection mechanism is missing, disabled, or ineffective.
For security-header scanning, CWE-693 is relevant because the application may be missing a browser security mechanism that could provide additional protection.

For example:

```
Missing Content-Security-Policy
        ↓
No CSP-based browser protection
        ↓
Reduced defense in depth
        ↓
Protection Mechanism Failure (CWE-693)
```

## 2. **Cross-Site Scripting (XSS)**
- **File:** `dash_penetration/scanner/xss.py`
- **Types Detected:**
  - Reflected XSS (exact payload matching)
  - Encoded XSS payload bypass
  - DOM-based XSS (static JavaScript analysis)
- **Test Payloads:** 15+ variations including encoded versions
- **False Positive Prevention:** Only flags exact payload reflection
- **Test Cases:** 8 comprehensive tests
- **CWE:** CWE-79


Cross-Site Scripting (XSS) is a web application vulnerability where attacker-controlled input is interpreted by a user's browser as executable JavaScript instead of being treated as ordinary data.


For example, an application might take a value from a URL parameter:

```
https://example.com/search?q=<script>alert(1)</script>
```

If the application places this input into the returned HTML without properly encoding or sanitizing it, the browser may interpret the injected content as JavaScript. XSS is primarily a client-side/browser vulnerability, but it is usually caused by unsafe handling of untrusted data by the web application.

A vulnerable data flow can be simplified as:

```
User-controlled input
        ↓
Web application
        ↓
HTML / JavaScript response
        ↓
Browser interprets input as code
        ↓
JavaScript executes
```

XSS can have serious consequences because JavaScript executes in the security context of the vulnerable web application. Depending on the application's architecture and protections, an attacker may be able to manipulate page content, perform actions as the victim, or access sensitive information available to client-side code.


### XSS Detection

The scanner checks for three main types of XSS:
  - Reflected XSS
  - Encoded XSS bypasses
  - DOM-based XSS

The scanner uses more than 15 payload variations and is designed to reduce false positives by requiring exact payload reflection for reflected-XSS findings.

#### Reflected XSS
Reflected XSS occurs when user-controlled input is immediately returned in an HTTP response and the browser can interpret that input as executable content.
A simplified example is:

```
Request
  ↓
?q=<payload>
  ↓
Application reflects parameter
  ↓
HTTP response contains <payload>
  ↓
Browser interprets the payload

For example, if an application receives:
?q=<script>alert(1)</script>
```

and returns:
```
<p>Search results for: <script>alert(1)</script></p>
```


the input has been reflected into the response without appropriate protection.


Detection approach

The scanner sends XSS test payloads through suitable input parameters and examines the resulting response. The important detection criterion is exact payload matching.

In other words, the scanner looks for evidence that the exact test payload supplied to the application was reflected back into the response.

This approach helps distinguish an actual reflection from unrelated text that merely happens to contain words or characters similar to an XSS payload.

#### Encoded XSS Payloads

Applications sometimes attempt to filter XSS by blocking obvious payloads or characters.
For example, an application might attempt to detect: `<script>`

but fail to account for encoded representations of attacker-controlled input.
The scanner therefore includes encoded XSS payload variations as part of its testing strategy.

The purpose is to determine whether an application's filtering or output handling can be bypassed when the same malicious input is represented differently. Conceptually:

```
Normal payload
      ↓
Application filtering
      ↓
Blocked

Encoded variation
      ↓
Application filtering
      ↓
Unexpectedly accepted/reflected
      ↓
Potential XSS
```

The scanner's 15+ payload variations, including encoded versions, provide broader coverage than testing only one obvious `<script>` payload.


#### DOM-Based XSS

DOM-based XSS occurs when client-side JavaScript takes attacker-controlled data and places it into a dangerous browser API or DOM context without adequate protection. Unlike reflected XSS, the vulnerability may not require the malicious input to appear in the server's HTTP response.

A simplified example:

```JS
const value = location.hash.substring(1);
document.write(value);
```

Here, data originating from the URL is passed directly into a DOM-writing operation.
The data flow is:

```
URL / browser-controlled source
        ↓
JavaScript
        ↓
DOM sink
        ↓
Potential script execution
```

Detection approach

The scanner performs static JavaScript analysis to look for potentially dangerous flows between browser-controlled sources and JavaScript/DOM sinks. This allows the scanner to identify potential DOM XSS even when the payload is not reflected by the server.

Because static analysis identifies suspicious code patterns rather than proving that an exploit will execute in every context, this type of detection generally requires more careful interpretation than an exact reflected-payload match.

#### Test Payloads

The scanner uses 15+ XSS payload variations, including encoded payloads. Using multiple payloads is important because applications can behave differently depending on:

- Characters contained in the payload
- HTML context
- JavaScript context
- Encoding
- Input filtering
- Output encoding
- Server-side sanitization
- Client-side processing

The payload set therefore provides broader coverage than relying on a single test string. The scanner should treat each payload as a distinct test case and associate a finding with the specific input that triggered the detection.

7. False Positive Prevention
A key feature of the reflected-XSS scanner is its exact payload matching.
The scanner does not simply report XSS because some suspicious-looking string appears in the response.

Instead, it checks whether the exact payload sent by the scanner is reflected in the response.

Conceptually:

```
Payload sent:
<test-payload>

Response:
<test-payload>
        ↓
Exact match
        ↓
Potential reflected XSS
```

Whereas:

Payload sent:

```
<test-payload>

Response:
some similar-looking text
        ↓
No exact match
        ↓
Do not report reflected XSS
```


This is an important false-positive prevention mechanism because normal application content may contain HTML-like strings, JavaScript keywords, or other text that resembles an XSS payload without actually being caused by the scanner's input.

Important limitation

Exact reflection is strong evidence that the application returns the supplied input, but reflection alone does not always prove that JavaScript will execute. For example, the payload could be returned inside a context where it is safely encoded or otherwise non-executable.

Therefore, the scanner's result should be interpreted as: The application reflected the test payload in a potentially dangerous manner; rather than automatically assuming that every reflection represents a successfully exploitable XSS vulnerability.


#### Test Cases
The XSS scanner is covered by 8 comprehensive tests. The tests should collectively verify the scanner's behavior across the major detection paths.

##### Reflected XSS
  - A vulnerable response containing the exact payload is detected.
  - A response that does not contain the payload is not reported.
  - Different payload variations are tested.
  - Encoded payload variations are handled correctly.

#### False-positive prevention

  - Similar but non-identical content does not trigger a finding.
  - Normal response content containing XSS-like text does not trigger a finding.
  - The scanner requires the expected relationship between the supplied payload and reflected response.


#### DOM-based XSS
Tests should verify that:
Suspicious JavaScript source-to-sink patterns can be identified.
JavaScript without a dangerous data flow is not incorrectly reported.
Static analysis does not automatically treat every use of a DOM API as exploitable XSS.
Together, these tests provide coverage for both server-side reflection and client-side JavaScript analysis.


### CWE-79 — Improper Neutralization of Input During Web Page Generation

CWE-79 describes Cross-Site Scripting (XSS) vulnerabilities caused by improperly handling untrusted input when generating web content.
The fundamental problem is:

```
Untrusted input
      ↓
Insufficient encoding / sanitization
      ↓
HTML or JavaScript context
      ↓
Browser interprets input as code
```

For dash-penetration, CWE-79 is the appropriate classification because the scanner is looking for cases where attacker-controlled input may be interpreted as executable content by the browser.


#### Summary
The XSS scanner therefore combines three detection strategies:

| Detection type | Main technique | Purpose |
|---|---|---|
| Reflected XSS | Exact payload reflection | Detect server responses that reflect attacker-controlled payloads |
| Encoded XSS | Encoded payload variations | Identify filtering/output-handling weaknesses involving encoded input |
| DOM-based XSS | Static JavaScript analysis | Identify potentially dangerous client-side source-to-sink data flows |


The overall goal is to identify potential XSS vulnerabilities while minimizing false positives, particularly by requiring exact payload reflection for reflected-XSS findings.

## Integration Guide

### Adding a New Scanner

1. **Create Scanner File**
   ```python
   # dash_penetration/scanner/my_scanner.py
   from .scanner import ScanResult, Severity
   
   class MyScanner:
       async def scan_url(self, url: str) -> list[ScanResult]:
           # Implement scanning logic
           pass
   ```

2. **Add to `__init__.py`**
   ```python
   from .my_scanner import MyScanner
   __all__ = [..., "MyScanner"]
   ```

3. **Integrate into `pentest_scanner.py`**
   ```python
   async with MyScanner(http_client) as scanner:
       results = await scanner.scan_url(url)
       for result in results:
           vulnerabilities.add_result(result)
   ```

4. **Write Tests**
   ```python
   # tests/test_my_scanner.py
   class TestMyScanner:
       def test_detection(self):
           # Test cases
   ```

5. **Test Locally**
   ```bash
   uv run pytest tests/test_my_scanner.py -v
   uv run python pentest_scanner.py https://test-app.com
   ```

## Key Architecture Decisions

### Why JavaScript Rendering First?

Modern web apps (React, Vue, Angular) render content client-side. The scanner uses Playwright to:
1. Execute JavaScript before testing
2. Discover hidden forms via button clicks
3. Monitor API endpoints via network requests
4. Analyze dynamically rendered content

### False Positive Prevention

Each scanner includes logic to minimize false positives:

- **XSS:** Only flags exact payload reflection, not generic `<script>` tags
- **Open Redirects:** Validates external domain, not internal redirects
- **CSRF:** Checks for presence of tokens, not just keywords
- **SQL Injection:** Looks for SQL error patterns, not random errors

### Async/Concurrent Testing

All scanners support `async/await` for concurrent requests:
- Tests multiple parameters simultaneously
- Reduces total scan time
- Uses connection pooling

## Troubleshooting

### Scanner Hangs on SPA

If Playwright times out on a Single Page Application:
- Increase `wait_time` in `js_crawler.py` (default: 3000ms)
- Check if app requires user interaction before rendering
- Verify network connectivity

### False Positives in Reports

If you see unexpected vulnerabilities:
- Check the "confidence" score (higher = more reliable)
- Review the "evidence" field for details
- Run specific scanner in isolation for debugging
- Check VULNERABILITY_ROADMAP.md for known false positive patterns

### Rate Limiting During Scan

If you get 429 (Too Many Requests) errors:
- Add delays in `HTTPClient` request loop
- Reduce number of parallel requests
- Scan during off-peak hours
- Use Rate Limiting scanner to understand limits
